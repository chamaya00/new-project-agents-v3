# Generating a page per tag without a custom Jekyll plugin

Research for issue #40, part of the tags objective (#39). Decision this
research has to serve: **whether a page can be generated for each tag in use
across `_posts` and `_projects`, with no custom Jekyll plugin and no other
change to how this repo is built or published, and if not, the smallest
mechanism that makes it possible** — so the designer and engineer children of
#39 (#41, #42) know what they're building against.

## Can this be done with core Jekyll?

**No, not with zero additional authoring per tag.** GitHub Pages' Jekyll
build runs with `safe: true` fixed and unchangeable, and "GitHub Pages cannot
build sites using unsupported plugins" — only a published whitelist of gems
is enabled, and unsupported plugins must be built locally and the static
output pushed instead, which this repo's whole approach (content files build
on GitHub's own infrastructure on every push, per ADR 0001) rules out
([About GitHub Pages and Jekyll](https://docs.github.com/en/pages/setting-up-a-github-pages-site-with-jekyll/about-github-pages-and-jekyll)).
That whitelist includes `jekyll-paginate` (numbered pages of N posts) but
nothing that discovers front-matter values across files and mints one output
page per distinct value — the thing plugins like `jekyll-archives` exist for
is exactly what's disallowed here.

The reason core Jekyll can't do this on its own is structural, not a missing
feature to work around: every output page in a plugin-free Jekyll build
traces back to one file on disk — a page, or a document inside a collection
directory (`_projects/`, `_posts/`, as `docs/research/content-listing.md`
already established). Nothing in core Jekyll walks the `tags` values across
*other* files and invents new output files from what it finds; that scan
step is precisely a Generator, which is plugin code, which is what `safe`
mode disables. So "a page per tag" cannot fall out of adding a `tags` field
to front matter alone, the way `_projects/<slug>.html` falls out of adding a
file to `_projects/`.

The smallest mechanism that stays inside the constraint is to make each
tag's page a file on disk too — one short stub per tag, in its own
collection, whose content is generated by Liquid rather than hand-typed. See
Options considered below.

## Options considered

Constraints, the same three `docs/research/content-listing.md` used: no
custom plugin gem, no edit under `.github/workflows/`, no change to this
repo's Pages publishing source (still branch-deployment).

### Option A: One stub file per tag, in a `_tags` collection

Add a `_tags` collection (declared in `_config.yml` next to `projects`,
`output: true`). Each tag in use gets one file, `_tags/<slug>.html`, whose
entire content is:

```
---
layout: tag
tag: photography
---
```

The `tag` layout does the actual work, using two Jekyll/Liquid filters that
ship with Jekyll itself (not a plugin, so unaffected by `safe: true`):
`where_exp`, whose own documented example is exactly this shape — filtering
an array to items whose array-valued property `contains` a given value
(`{{ site.members | where_exp:"item", "item.projects contains 'foo'" }}`,
[Jekyll: Filters](https://jekyllrb.com/docs/liquid/filters/)) — and `concat`,
standard Liquid, which merges two arrays
([Liquid: concat](https://shopify.github.io/liquid/filters/concat/)). See
Cross-collection lookup below for the exact expression.

- **What it does**: adding `tags: [photography]` to a post or project's front
  matter is the entire content-author action for an *existing* tag — the tag
  page picks it up on the next push with no other edit, the same "one file,
  nothing else" property `_projects`/`_posts` already have. A *new* tag
  needs its one-time, one-line stub file, analogous to `_projects`/`_posts`
  needing their directory to exist in the first place, just at the grain of
  a tag rather than a collection.
- **What it costs**: a `_tags` collection declaration, a `tag` layout, and
  that one stub file per distinct tag, created when the tag is first used.
- **What it rules out later**: a tag page existing with no entries under it
  — see Avoiding pages for unused tags below, since the stub file's presence
  and the tag's actual usage in content can now drift apart if only one side
  is edited.
- **What would have to be true to be right**: that a one-line file per
  *distinct tag* (expected to be a small, slow-growing set on a personal
  portfolio site) is an acceptable recurring cost, in exchange for needing no
  plugin, no workflow edit, and no Pages source change.

### Option B: A single tags index page with in-page anchors, no per-tag files

One hand-written `tags.html`, listing every distinct tag Liquid can compute
at build time (`site.posts | concat: site.projects | map: "tags" | compact |
flatten | uniq`, all core Liquid/Jekyll filters) as a heading per tag, each
followed by its filtered entry list inline, with an `id` anchor
(`<h2 id="photography">`) instead of its own URL.

- **What it does**: needs no collection, no stub files, and no layout beyond
  what's already hand-typed once — genuinely zero marginal file cost as tags
  are added or dropped, since the whole list is recomputed from content on
  every build.
- **What it costs**: no tag gets a real page. `#photography` is a fragment
  of `tags.html`, not a resource with its own URL — it can't be linked,
  bookmarked, or crawled independently of every other tag's content loading
  first, and `tags.html` itself grows without bound as entries and tags
  accumulate, unlike Option A where each tag's page is its own file.
- **What it rules out**: everything the issue title and #39 ask for. The
  issue frames this as one level up from "a page per collection" — a page
  *per tag* — and the objective's acceptance bar talks about "a tag's page"
  in the singular, implying a distinct resource per tag. This option
  produces a tag *section*, not a tag *page*.
- **What would have to be true to be right**: that a fragment identifier on
  a shared page satisfies "a page per tag" — it doesn't, under the plain
  reading of #39 and this issue's own title, so this option is rejected on
  that basis rather than on any technical shortcoming.

### Custom plugin, for completeness

Noted rather than compared as a real option, since the issue's own
constraint rules it out directly: a Ruby Generator plugin (the mechanism
`jekyll-archives` itself uses) *could* scan `site.posts`/`site.projects` at
build time and mint a page per discovered tag with zero per-tag files —
closing exactly the gap Option A's stub files patch by hand. It's excluded
outright, not on cost or tradeoff grounds: GitHub Pages' build runs
`safe: true`, fixed, and does not build sites using unsupported plugins
(cited above) — there is no version of this option that runs on GitHub's
own infrastructure the way this repo is built today.

## Cross-collection lookup

A tag's page has to list every entry carrying it regardless of whether the
entry is a post or a project — the same cross-collection requirement Home's
Recent area already has (`index.html`, ADR 0001), solved there by rendering
each collection's entries through the same `_includes/entry.html` partial.
The tag layout does the equivalent for a single combined, filtered list:

```liquid
{%- assign tagged = site.posts | concat: site.projects
  | where_exp: "entry", "entry.tags contains page.tag"
  | sort: "date" | reverse -%}
{%- if tagged.size > 0 %}
<ul class="entry-list">
  {%- for entry in tagged %}
  {% include entry.html entry=entry %}
  {%- endfor %}
</ul>
{%- else %}
<p class="empty-state">No entries tagged "{{ page.tag }}" yet.</p>
{%- endif %}
```

`concat` merges both collections into one array before filtering, so
`where_exp` only has to run once, against entries of both types
interchangeably — it reads `entry.tags` the same way whether `entry` is a
post or a project, since both carry the field under the same name (see Front
matter below). `sort: "date" | reverse` is needed because the concatenated
array loses `site.posts`' own free most-recent-first ordering the moment it's
merged with `site.projects` (same reason `index.html`'s Recent area and
`projects.html` already sort projects by `date` explicitly, per
`tests/check.sh`'s ordering checks). The same `entry.html` partial the
listing pages and Home already use renders each match, so a tagged project
and a tagged post appear identically on the tag page — no new rendering path
to keep in sync with the existing one.

## Avoiding pages for unused tags

A stub file's mere presence in `_tags/` is what makes Jekyll emit a page for
it — front matter is static YAML, read before any Liquid runs, so nothing in
core Jekyll can conditionally skip emitting a collection document's output
based on a computation over other files' content. That means "no stub file →
no page" is automatic and free (an unused tag that has never had a stub file
created for it produces nothing, the same as an empty `_projects/` directory
today), but the reverse direction — a tag falling out of use while its stub
file is left behind — is **not** automatically caught. The stub file would
keep building a real, reachable page whose entry list is empty.

The mechanism itself can't close that gap without a plugin (the same
build-time content scan Option A was chosen to avoid needing), so it's a
process rule rather than a build guarantee: removing the last entry that
carries a tag, in the same commit, removes that tag's `_tags/<slug>.html`
stub. This is the one place this recommendation is weaker than the "page
per collection" precedent it's built on — `_projects`/`_posts` never have
this drift, because there's no separate file whose existence has to be kept
in sync with content.

## Front matter

Two distinct fields, on two distinct kinds of file:

- **On entries** (`_posts/*.html`, `_projects/*.html`): an optional `tags`
  field, a YAML list of strings, e.g. `tags: [photography, travel]`. Sits
  alongside the `title`, `date`, `layout`, and optional `summary` fields
  `docs/research/content-listing.md` already established — no change to any
  of those. An entry with no `tags` key (or an empty list) has
  `entry.tags` come back `nil`/empty in Liquid, which is what a "renders no
  tag area" check on the entry itself (#41's concern, not this doc's) would
  branch on — `{% if entry.tags.size > 0 %}`, the same pattern
  `_includes/entry.html` already uses for the optional `summary` field.
- **On tag stub files** (`_tags/*.html`): a required `tag` field, a single
  string naming the exact tag the page is for (matched verbatim against
  entries' `tags` list entries — no case-folding or slugification layer is
  proposed here), and `layout: tag`. No `title`/`date`/`summary` — a tag
  page isn't an entry and isn't listed by `entry.html` anywhere.

## Consequences

- **Schema change, ADR required.** This adds a new front-matter field
  (`tags`, on both collections) and a new collection (`_tags`, declared in
  `_config.yml`), which is a data-shape change per the house rules' "any
  change to a schema, a data shape, or a dependency gets an ADR." Written up
  in [`docs/decisions/0002-add-tags-and-a-tag-page-per-collection.md`](../decisions/0002-add-tags-and-a-tag-page-per-collection.md),
  status `proposed` — same convention ADR 0001 used: it moves to `accepted`
  in the diff that actually commits `_config.yml`'s `_tags` collection and
  the `tag` layout, not in this research diff.
- **No new dependency.** Unlike Option A of `content-listing.md` (which
  added Jekyll itself), this recommendation adds no gem, no `Gemfile` entry,
  and no plugin — `where_exp` and `concat` ship with Jekyll/Liquid core,
  already present since ADR 0001. CLAUDE.md's Stack section needs no further
  change beyond what ADR 0001 already made true.
- **New per-tag maintenance step.** Every distinct tag now has a
  corresponding file that must exist while the tag is in use and be removed
  when it falls out of use — a manual bookkeeping step this repo doesn't
  currently have anywhere else, and the mechanism cannot enforce on its own
  (see Avoiding pages for unused tags above). This is the cost the
  Recommendation below weighs against the alternative.

## Recommendation

**Option A — one stub file per tag under a new `_tags` collection**, each
rendering a `where_exp`/`concat` cross-collection filter through the
existing `entry.html` partial. It's the only option that produces an actual
page per tag (Option B doesn't) without a plugin GitHub Pages won't run (the
custom-generator option doesn't run at all).

The strongest argument against it: the "no page for an unused tag"
guarantee the objective asks for is enforced by a commit-discipline
convention, not by the build — a stub file left behind after its last
tagged entry is removed produces a real, reachable, permanently-empty page
that nothing in this mechanism, or `tests/check.sh`, would catch on its own
unless a check is written specifically to compare `_tags/` stub files
against tags actually in use across `_posts`/`_projects`.
