# ADR 0001: Enable Jekyll to generate project/post listings from content files

Date: 2026-09-08
Status: proposed

## Context

Objective #3 requires that adding a single project or post content file, with
no other change, makes it appear in its section's listing and as a recent
entry on Home. CLAUDE.md's current Stack (static HTML5 + CSS3, no
JavaScript, no build step, no package manager) has no actor that can notice a
new file and update a separate listing page — `docs/research/content-listing.md`
(issue #11) establishes that this is not achievable as-is and compares three
mechanisms that would make it achievable.

## Decision

Enable Jekyll processing on this repo's existing GitHub Pages branch-deployment
source (remove `.nojekyll`, add a minimal `_config.yml`), and define two
Jekyll collections: `_posts/` (built in) for posts, `_projects/` (declared in
`_config.yml`) for projects. Content files stay hand-authored HTML5 with a
front-matter header: `title` and `layout` on every file, `date`
(`YYYY-MM-DD`) on projects (posts get their date from the filename), and an
optional `summary` for listing/recent-entry cards. Listing pages and Home's
recent-entries section become Liquid templates that iterate the collections,
generated by GitHub's own Pages build on every push.

## Consequences

This makes "add one file, nothing else" true, and needs no workflow file
under `.github/workflows/` and no change to the repo's Pages publishing
source — both of which the rejected alternatives required. It makes local
preview harder: `python3 -m http.server` (CLAUDE.md's current Dev command)
no longer renders listing/Home pages correctly without also running Jekyll
locally, which needs Ruby/Bundler. It also reopens a call `pages-subpath.md`
made under the opposite assumption: with Jekyll running, `relative_url`/
`site.baseurl` become the recommended way to link *generated* pages (their
output nests at varying depth, e.g. `/projects/<slug>/`), while hand-authored
pages outside the collections keep the existing hand-typed relative-link
convention. CLAUDE.md's Stack section needs "no build step" dropped and "no
JavaScript, no framework" qualified to describe Jekyll's Liquid templating as
GitHub-hosted, not repo-maintained, build machinery. This ADR moves to
`accepted` in the same diff that actually commits `_config.yml` and removes
`.nojekyll`.

## Alternatives rejected

- **A bespoke generator script run by a custom GitHub Actions build-and-deploy
  workflow**: rejected because it requires editing `.github/workflows/` and
  changing the repo's Pages publishing source to "GitHub Actions" — both
  outside every agent role's reach per the house rules, so no designer or
  engineer child of #3 could finish implementing it unassisted.
- **Client-side fetch of GitHub's contents API (or a hand-maintained
  manifest) at page load**: rejected because a hand-maintained manifest is a
  second manual edit (fails "nothing else" outright), and the live-API
  variant requires JavaScript (breaking the no-JS-visitor case, with no
  static fallback) and is capped by GitHub's unauthenticated REST API limit
  of 60 requests/hour per IP address, which ordinary shared-NAT traffic to a
  public portfolio site can exhaust.
